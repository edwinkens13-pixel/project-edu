What this website uses today

The letter writer is built with HTML, CSS, and browser JavaScript and is published on GitHub Pages. Drafts are browser-local and shareable conversations travel in links. The optional AI features use a PowerShell server-side OpenAI proxy when running locally; GitHub Pages cannot run that backend. React and a database are learning concepts and a suggested growth path, while this project uses GitHub for source control and static hosting.

⌘In use today

HTML

The meaning and structure

Semantic elements give the app its content, forms, navigation, labels, and accessible page outline.

How it fits

Use landmarks such as main, nav, and section. Associate labels with controls so assistive technology and browsers understand the interface.

◈In use today

CSS

The visual system

Layouts, responsive breakpoints, typography, colors, interaction feedback, and reduced-motion support.

How it fits

Keep styles consistent with design tokens, use flexible grid and flex layouts, and check contrast and keyboard focus as well as appearance.

⚡In use today

JavaScript

The behavior and state

Updates the letter preview, saves drafts locally, builds share links, opens chat, and calls the AI endpoint.

How it fits

Validate input, update the interface from explicit state, handle network errors visibly, and use text rendering for user content rather than inserting it as HTML.

⚛Growth path

React

A component-based frontend

A modern React app could divide the editor into reusable components and keep form and conversation state explicit.

How it fits

React is not loaded by the current site. For a rebuild, use React with TypeScript, Vite, accessible components, tested forms, and a small set of clearly owned state.

⑂In use today

Git

Track and safely evolve code

Commits record coherent changes; branches make it safer to experiment and review before merging.

How it fits

This project uses Git for version history. Use focused commits, review diffs, keep secrets out of history, and avoid force-pushing shared work.

◉In use today

GitHub

Collaborate and automate

Host a repository, review pull requests, track work, and run automated checks with GitHub Actions.

How it fits

Protect the main branch, require checks and review for changes, use Dependabot or equivalent dependency monitoring, and keep deployment secrets in a secret store—not in source files.

⇄Small local API today

Backend

Trusted server-side operations

The current PowerShell server serves pages and proxies optional AI requests without exposing the API key in browser code.

How it fits

A growth path could use a typed Node.js API, validate each request, authenticate users where needed, apply rate limits, and enforce authorization on every conversation operation.

▤Growth path

Database

Durable shared information

The current app does not store conversations in an online database. PostgreSQL could power account-backed shared threads.

How it fits

Model users, conversations, participants, and messages; use migrations, foreign keys, least-privilege database roles, parameterized queries, backups, and retention rules.

♢Every layer

Web security

Protect people and their data

Security includes safe rendering, validation, secrets handling, access control, transport security, and resilient dependencies.

How it fits

Use HTTPS, secure and HttpOnly cookies when applicable, CSRF protections for cookie-authenticated writes, output encoding, server-side authorization, secure headers, logging without secrets, and regular dependency updates.

☁Deployment concept

Hosting & deployment

Deliver the app reliably

Publish the frontend over HTTPS, deploy the API separately if needed, and configure production environment variables.

How it fits

A common architecture uses a static frontend host/CDN, a managed backend service, and managed PostgreSQL. CI can test and build on pull requests, then deploy from a protected main branch. No hosting account is connected here yet.

Build with confidence

Git → GitHub → deployment

A small, repeatable workflow helps teams ship improvements without losing track of what changed.

Track a focused change

Example commands for a local project you own. Review the changes before committing.

git status
git add index.html letter.html home.html technology.html terms.html README.md server.ps1 cat-background.jpg
git commit -m "Update website"
git push origin main

Review git status and scan staged files for secrets before committing. Never add API keys or credentials.

Built in, not bolted on

A practical security baseline

Security is a system of small controls across the browser, server, data store, and release process.

Protect secretsKeep API keys in server environment variables or a managed secret store, never frontend files or Git history.
Validate at the APICheck types, lengths, ownership, and permissions on the server; browser validation is only a usability aid.
Render user content as textEscape output, avoid unsafe HTML insertion, and use parameterized database queries.
Limit accessAuthenticate and authorize each private conversation; use least privilege and safe session handling.
Use HTTPS and headersEncrypt traffic and set appropriate content, framing, referrer, and transport security policies.
Monitor and recoverKeep dependencies current, log useful events without secrets, back up data, and test restoration.

Learning note: the current local demo intentionally does not have user accounts or an online database. Publishing the static site does not automatically make its link-based conversations private or add server-side account security. A production shared inbox needs a deliberate backend, access-control model, privacy policy, and security review.
